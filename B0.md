# B0 — The count trap

## Observed plan

The supplied plan overrides landlord_accounts with ["la-001", "la-003", "la-004"], removing la-002 without editing variables.tf. It compares configuration with the seeded state using refresh=false; no apply has been performed.

Terraform identifies count instances by their numeric address, not by their bucket name or landlord_account_id tag. Removing a middle list entry changes the account selected at every later index.

| Current count address | Bucket/account in seeded state | Account desired after removal | Observed action |
|---|---|---|---|
| aws_s3_bucket.landlord_media[0] | haven-media-la-001 / la-001 | la-001 | No change |
| aws_s3_bucket.landlord_media[1] | haven-media-la-002 / la-002 | la-003 | Destroy and recreate |
| aws_s3_bucket.landlord_media[2] | haven-media-la-003 / la-003 | la-004 | Destroy and recreate |
| aws_s3_bucket.landlord_media[3] | haven-media-la-004 / la-004 | None | Destroy: index out of range |

At [1], the bucket name changes from haven-media-la-002 to haven-media-la-003. At [2], it changes from haven-media-la-003 to haven-media-la-004. The AWS provider marks both name changes as forcing replacement because S3 buckets cannot be renamed in place. Index [3] is removed because count falls from four to three. Index [0] remains unchanged and is omitted from the change listing.

The full summary is **4 to add, 0 to change, 3 to destroy**:

- Two additions and two destructions come from the replacements at [1] and [2].
- One further destruction removes [3].
- Two further additions create aws_s3_bucket.listing_media and aws_s3_bucket_lifecycle_configuration.listing_media_archive from lifecycle.tf. Those B1 resources are configured but absent from the seeded state; their creation is unrelated to the account removal.

A replacement counts as an addition and a destruction, not an in-place change. The -/+ symbol specifies destroy then create. Values marked “known after apply” are computed/unknown values, not additional resources or separate evidence of replacements.

## Why this is dangerous

Removing la-002 should not recreate buckets belonging to surviving accounts la-003 and la-004. Here, positional identity causes those accounts' existing infrastructure to be scheduled for destruction. In a real account this risks interruption, failed operations, and loss of stored media if deletion is permitted. With force_destroy=false, a non-empty S3 bucket normally blocks deletion; that is not a safe migration strategy. Existing globally unique bucket names can also cause creation conflicts. Replacement does not transfer objects to the new bucket.

This plan uses dummy credentials and seeded state, so it demonstrates Terraform's proposed changes, not verified live AWS resources or successful deletions. Do not apply this destructive demonstration.

## Fix: stable account-ID keys and explicit migration

Use for_each keyed by each stable landlord account ID, for example for_each = toset(var.landlord_accounts), with bucket = "haven-media-${each.key}" and landlord_account_id = each.key in the tags. This is a proposed design only; Terraform configuration has not been modified.

A keyed address identifies an account regardless of list position. Reordering the list does not reassign instances. Removing la-002 then removes only its keyed instance; la-001, la-003, and la-004 keep their identities. Actual account deletion still requires a deliberate data-retention and bucket-deletion decision.

Changing count to for_each alone is insufficient: the existing state contains numeric addresses. Without explicit moves, Terraform sees different old and new addresses and may propose destroying old instances and creating new ones.

The migration must preserve the ORIGINAL state ownership, as follows:

| Existing count address | New account-keyed address | Bucket preserved |
|---|---|---|
| aws_s3_bucket.landlord_media[0] | aws_s3_bucket.landlord_media["la-001"] | haven-media-la-001 |
| aws_s3_bucket.landlord_media[1] | aws_s3_bucket.landlord_media["la-002"] | haven-media-la-002 |
| aws_s3_bucket.landlord_media[2] | aws_s3_bucket.landlord_media["la-003"] | haven-media-la-003 |
| aws_s3_bucket.landlord_media[3] | aws_s3_bucket.landlord_media["la-004"] | haven-media-la-004 |

In particular, [1] must map to la-002, NOT la-003 from the shortened input list. [2] must map to la-003, NOT la-004.

For a real migration, switch to keyed configuration and declare all four address moves together while retaining all four accounts. Declarative moved blocks can express these mappings without manually editing the state. Review that plan for identity preservation before considering account removal as a separate change. State records the new addresses only when the migration is applied. This assessment's protected seeded terraform.tfstate must remain untouched; the mapping here documents the migration rather than executing it.
